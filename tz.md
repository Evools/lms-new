# Техническое задание: модуль «Документооборот и отчётность» для LMS

## 1. Цель разработки

Разработать в существующей LMS отдельный модуль «Документооборот и отчётность», предназначенный для автоматизированного создания, заполнения, редактирования, согласования, хранения и экспорта документов, необходимых для организации учебного процесса.

Модуль должен использовать существующую базу данных LMS и автоматически подставлять информацию о студентах, учебных группах, преподавателях, мастерах производственного обучения, посещаемости, успеваемости и других учебных показателях.

Основная цель — сократить ручную работу сотрудников учебного заведения при подготовке рапортов, справок, ведомостей и аналитических отчётов.

## 2. Основные требования

Перед началом разработки необходимо изучить текущую архитектуру LMS, существующую структуру базы данных, систему авторизации, ролевую модель, интерфейс и используемый технологический стек.

**Важно:** модуль должен интегрироваться в существующий проект. Необходимо повторно использовать имеющиеся сущности, компоненты, стили и механизмы авторизации. Не создавать дублирующие таблицы студентов, групп, преподавателей и других уже существующих объектов без технической необходимости.

## 3. Основные разделы модуля

### 3.1. Главная страница документооборота

Создать страницу со следующими разделами:

- Создать документ.
- Мои документы.
- Все документы — для пользователей с соответствующими правами.
- Шаблоны документов.
- Отчёты и аналитика.
- Архив документов.

На главной странице отображать:
- количество созданных документов;
- количество черновиков;
- документы, ожидающие согласования;
- подписанные или утверждённые документы;
- последние созданные документы;
- быстрые действия для создания популярных документов.

Предусмотреть поиск по названию, номеру, типу документа, студенту, группе, автору и дате создания. Добавить фильтрацию по статусу и периоду.

### 3.2. Создание документов

Реализовать универсальный механизм создания документов на основе шаблонов.

Пользователь должен иметь возможность:

1. Выбрать тип документа.
2. Выбрать одного или нескольких студентов, группу либо другой необходимый объект.
3. Указать причину, основание, дату и дополнительные сведения.
4. Автоматически заполнить документ данными из LMS.
5. Проверить и при необходимости отредактировать доступные поля.
6. Просмотреть итоговый документ перед сохранением.
7. Сохранить документ как черновик.
8. Сформировать финальную версию.
9. Скачать документ в PDF или DOCX.
10. Распечатать документ.
11. Вернуться к документу для дальнейшей работы в пределах предоставленных прав.

Форма создания должна динамически изменяться в зависимости от типа документа. Не показывать пользователю поля, которые не относятся к выбранному шаблону.

### 3.3. Категории документов

Предусмотреть возможность расширения списка типов документов.

**А. Рапорты и служебные документы**
- Рапорт на отчисление одного студента.
- Групповой рапорт на отчисление нескольких студентов.
- Рапорт о систематических пропусках занятий.
- Рапорт о низкой успеваемости.
- Рапорт о переводе студента в другую группу.
- Рапорт о восстановлении студента.
- Служебная записка.
- Докладная записка.
- Заявление или сопроводительный документ, если это предусмотрено внутренними правилами учреждения.

**Б. Документы по учебной деятельности**
- Список студентов группы.
- Список студентов с задолженностями.
- Ведомость успеваемости.
- Сводная ведомость по предметам.
- Отчёт о посещаемости.
- Отчёт об успеваемости за выбранный период.
- Отчёт по выполнению учебного плана.
- Отчёт по производственному обучению и практике.
- Список студентов, претендующих на стипендию, по установленным критериям.
- Сводный отчёт по группе или курсу.

**В. Документы куратора и мастера производственного обучения**
- Характеристика на студента.
- Характеристики на нескольких студентов по отдельности.
- Отчёт о работе куратора или мастера.
- Отчёт о посещаемости закреплённой группы.
- Отчёт о проделанной воспитательной работе.
- Список студентов, требующих дополнительного контроля.
- Сводка по успеваемости и посещаемости группы.

**Г. Административные и аналитические отчёты**
- Сводка по всем группам.
- Сводка по количеству студентов.
- Отчёт по отчислениям, переводам и восстановлениям.
- Сводный отчёт по задолженностям.
- Отчёт за месяц, семестр или учебный год.
- Отчёт по преподавателям и учебным дисциплинам в рамках разрешённых полномочий.

Перечисленные документы являются стартовым набором. Предусмотреть добавление новых типов и шаблонов без переписывания основного механизма модуля.

## 4. Работа с несколькими студентами

Особое внимание уделить групповым документам.

Например, при создании рапорта на отчисление пользователь должен иметь возможность выбрать одного или нескольких студентов из списка.

Система должна:
- отображать ФИО, группу и другие необходимые сведения;
- поддерживать поиск и фильтрацию студентов;
- позволять выбирать студентов из одной или нескольких групп, если это допускается типом документа;
- автоматически формировать таблицу со студентами;
- предоставлять возможность указать индивидуальную причину для каждого студента;
- поддерживать общую причину для всех выбранных студентов;
- проверять наличие обязательных данных;
- формировать единый документ с перечнем студентов, если шаблон это допускает;
- позволять сформировать отдельный документ для каждого студента при необходимости.

Создание рапорта само по себе не должно автоматически отчислять студента. Изменение статуса обучения выполняется отдельной операцией уполномоченным сотрудником после необходимого согласования.

## 5. Система шаблонов документов

Реализовать управление шаблонами документов.

Администратор или другой уполномоченный сотрудник должен иметь возможность:
- создавать шаблоны;
- редактировать шаблоны;
- копировать существующие шаблоны;
- активировать и архивировать шаблоны;
- задавать название, категорию и описание;
- определять обязательные и необязательные поля;
- указывать, какие данные автоматически подставляются из LMS;
- настраивать текстовые блоки, таблицы и подписи;
- выбирать формат итогового документа.

Предусмотреть переменные для автоматического заполнения, например:

- ФИО студента;
- номер личного дела или другой предусмотренный идентификатор;
- название группы;
- специальность;
- курс;
- учебный год;
- ФИО мастера производственного обучения;
- ФИО руководителя;
- дата составления;
- причина составления;
- список выбранных студентов;
- период отчёта;
- показатели посещаемости и успеваемости.

Использовать систему переменных и повторяемых строк таблиц. Не привязывать каждый тип документа к отдельному жёстко запрограммированному компоненту, если его можно реализовать через общий механизм шаблонов.

## 6. Формирование и экспорт документов

Предусмотреть следующие возможности:

- Предварительный просмотр.
- Экспорт в PDF.
- Экспорт в DOCX.
- Печать с корректным форматированием.
- Поддержка русского и кыргызского языков.
- Корректное отображение кириллицы.
- Форматирование официальных документов: поля страницы, шрифт, интервалы, заголовки, таблицы, даты и блоки подписей.
- Нумерация страниц для многостраничных документов.
- Сохранение итоговой версии документа в архиве LMS.

При экспорте DOCX документ должен оставаться пригодным для дальнейшего редактирования в Microsoft Word.

PDF должен сохранять структуру документа и корректно отображаться при печати.

## 7. Согласование документов

Реализовать настраиваемый процесс согласования.

Пример процесса:

Черновик → На согласовании → Одобрен / Отклонён → Финальная версия.

В зависимости от типа документа могут участвовать мастер производственного обучения, заведующий отделением, учебная часть, заместитель директора или директор.

Требования:
- возможность назначить согласующих;
- просмотр документа согласующим;
- одобрение или отклонение;
- указание комментария при отклонении;
- фиксация даты и пользователя, выполнившего действие;
- история изменения статусов;
- уведомление ответственных пользователей внутри LMS, если механизм уведомлений уже существует.

Маршрут согласования должен настраиваться в зависимости от типа документа и регламента учреждения.

Не считать обычное одобрение в LMS юридически значимой электронной подписью. Если потребуется электронная подпись, её реализацию определить отдельным этапом.

## 8. Роли и права доступа

Интегрировать модуль с существующей системой ролей LMS.

Пример распределения прав:

**Мастер производственного обучения / куратор**
- Создание документов по закреплённым группам.
- Просмотр разрешённых данных своих студентов.
- Создание характеристик и отчётов.
- Просмотр собственных документов и их статусов.

**Преподаватель**
- Создание разрешённых учебных отчётов.
- Просмотр данных по закреплённым дисциплинам и группам.

**Учебная часть**
- Создание и обработка документов в пределах полномочий.
- Формирование сводных отчётов.
- Работа с документами нескольких групп.

**Администрация**
- Просмотр документов в пределах предоставленных полномочий.
- Согласование и утверждение.
- Доступ к общим отчётам.

**Администратор LMS**
- Управление шаблонами, настройками и правами модуля.

Это предварительная модель. Окончательные полномочия должны соответствовать существующей ролевой модели LMS и внутренним правилам учреждения.

Обязательно реализовать проверку доступа на серверной стороне. Скрытия кнопок в интерфейсе недостаточно.

## 9. История изменений и архив

Для каждого документа хранить:
- уникальный идентификатор;
- тип и название;
- номер документа, если предусмотрен;
- автора;
- дату создания и последнего изменения;
- выбранных студентов или другие связанные объекты;
- текущий статус;
- историю согласования;
- версию шаблона;
- итоговый файл или возможность воспроизвести документ по сохранённой версии;
- историю значимых изменений.

После утверждения документа его содержимое должно сохраняться как отдельная версия. Изменение исходных данных в LMS не должно незаметно менять уже сформированный и утверждённый документ.

Предусмотреть архивирование и поиск ранее созданных документов.

Удаление утверждённых документов обычными пользователями запретить. Политику хранения и удаления определить с учётом правил учреждения.

## 10. Отчёты и аналитика

Реализовать механизм формирования отчётов по фильтрам:
- учебный год;
- семестр;
- период;
- группа;
- курс;
- специальность;
- дисциплина;
- студент;
- преподаватель или мастер;
- тип отчёта.

Для отчётов по посещаемости и успеваемости автоматически рассчитывать показатели на основе имеющихся данных LMS.

Для каждого показателя определить формулу расчёта, учитываемые статусы и правила обработки отсутствующих данных.

Если информация отсутствует в базе, система не должна придумывать значения или считать отсутствие данных нулевым результатом без явно установленного правила.

Результаты должны быть доступны для просмотра, печати и экспорта в PDF, DOCX или XLSX в зависимости от назначения отчёта.

## 11. Интерфейс и пользовательский опыт

Сохранить существующий дизайн-системный подход LMS.

Требования к интерфейсу:
- минималистичный и понятный дизайн;
- использование существующих компонентов;
- удобная работа с длинными списками студентов;
- поиск и фильтрация без перезагрузки страницы, если это соответствует текущей архитектуре;
- пошаговое создание сложных документов;
- понятная валидация;
- автоматическое сохранение черновика или явная возможность сохранить его;
- подтверждение действий, которые меняют статус документа;
- корректная работа на компьютерах и планшетах.

Не перегружать интерфейс большим количеством карточек, лишними анимациями и декоративными элементами.

## 12. Технические требования

Использовать существующий стек проекта и его архитектурные соглашения.

Если проект использует Next.js, TypeScript, Prisma, PostgreSQL и shadcn/ui, продолжить работу с этими технологиями без внедрения альтернативного стека без необходимости.

Требования:
- строгая типизация TypeScript;
- отсутствие `any` без обоснованной необходимости;
- переиспользуемые компоненты;
- разделение бизнес-логики, UI и доступа к данным;
- серверная проверка прав;
- валидация данных;
- транзакции для связанных изменений;
- корректная обработка ошибок;
- индексы базы данных для основных фильтров;
- тестирование бизнес-логики, формирования документов и разграничения доступа;
- отсутствие дублирования существующих сущностей LMS.

Предусмотреть отдельные сущности базы данных для документов, шаблонов, версий, согласований и связанных записей, адаптировав их к существующей схеме проекта.

Не создавать новые модели до изучения текущей схемы Prisma и связей между существующими моделями.

## 13. Безопасность

Документы могут содержать персональные данные студентов.

Обязательно:
- ограничить доступ к документам по ролям и связям с учебными группами;
- проверять права при чтении, создании, изменении, экспорте и согласовании;
- защищать экспортируемые файлы от доступа посторонних пользователей;
- фиксировать значимые действия в журнале аудита;
- исключить утечку персональных данных через логи и сообщения об ошибках;
- не допускать массовой выгрузки данных пользователями без соответствующих полномочий.

- Реализовать экспорт PDF и DOCX.

**Этап 4. Первые документы**

**Этап 6. Расширенная отчётность**

**Этап 7. Тестирование**
- Проверить права доступа.

- Проверить экспорт русскоязычных и кыргызскоязычных документов.
- Проверить работу с одним и несколькими студентами.
- Проверить сохранение утверждённых версий.

## 15. Критерии приёмки

Модуль считается готовым к первой версии, если:

1. Пользователь с соответствующими правами может создать документ из шаблона.
2. Данные студентов и групп автоматически подставляются из LMS.
3. Можно создать документ на одного или нескольких студентов.
4. Документ можно сохранить как черновик, отредактировать и сформировать финальную версию.
5. Доступны предварительный просмотр, PDF и DOCX.
6. Работает поиск, фильтрация и архив.
7. Реализовано разграничение прав на серверной стороне.
8. Утверждённые версии не изменяются автоматически при обновлении данных LMS.
9. Отчёты формируются по установленным правилам расчёта.
10. Все основные действия протестированы.
11. Модуль работает с существующей базой данных и не нарушает текущую функциональность LMS.
12. Добавление нового шаблона не требует переписывания ядра документооборота.

## 16. Инструкции разработчику или ИИ

Не начинай с массового изменения кода.

Сначала изучи существующий проект, затем предложи архитектуру интеграции, схему данных, список переиспользуемых компонентов и последовательность реализации.

После согласования плана реализуй модуль поэтапно. На каждом этапе проверяй типизацию, миграции, права доступа и работоспособность существующих функций.

Не используй фиктивные данные вместо реальных сущностей LMS в рабочей реализации. Не создавай несуществующие поля и связи на основании предположений.

Если для конкретного документа необходимых данных в LMS нет, явно укажи это и предусмотрите ручное заполнение соответствующих полей.

Итоговая задача — создать расширяемую систему документооборота, которую можно постепенно дополнять новыми формами и отчётами без переписывания основного модуля.
